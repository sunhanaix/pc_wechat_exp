# WeChat 4.1.10.x Database Key Extraction — Design Spec

**Goal:** Adapt database key extraction to work with WeChat 4.1.10.x by adding MMKV-based offline extraction as the primary strategy, while preserving existing memory-scanning as fallback for older versions.

**Architecture:** Add `_extract_keys_from_mmkv()` to `src/key_scan.py` that reads encrypted MMKV config files from `db_storage/MMKV/`, derives AES-GCM keys via `MD5(code+wxid)`, decrypts them, extracts DB encryption keys, and verifies via HMAC. The existing `run_key_scan()` entry point gains an MMKV-first strategy: try MMKV extraction first, then fall through to memory scanning for any remaining salts.

**Tech Stack:** Python 3.8+, pycryptodome (AES-GCM), existing `verify_enc_key()` for HMAC verification.

---

## 1. Root Cause Summary

WeChat 4.1.10.27 changed its key management architecture:
- **Old (4.1.9):** Keys stored as SQL hex literals `x'<64hex_key><32hex_salt>'` in `Weixin.dll` heap memory
- **New (4.1.10.x):** Keys NOT in any readable process memory — neither raw bytes, hex strings, XOR-obfuscated forms, nor base64. Confirmed via 6-phase diagnostic scanning 845 MB across 5 processes with 0 hits for known key bytes.
- **Key finding:** Database keys are now stored in AES-GCM-encrypted MMKV configuration files at `db_storage/MMKV/` (Tencent's key-value store). The MMKV encryption key is derived via `MD5(code + wxid_clean)`.

## 2. Architecture

```
run_key_scan(db_dir, out_file)
    │
    ├─ collect_db_files(db_dir)  ── [EXISTING]
    │
    ├─ _extract_keys_from_mmkv(db_dir, db_files, salt_to_dbs)
    │      ├─ Scan db_storage/MMKV/ for .mmkv files
    │      ├─ Extract codes from filenames (e.g., f2540600tinfo.mmkv → code=0x2540600)
    │      ├─ Derive AES-128 key: MD5(str(code) + wxid_clean).hex()[:16]
    │      ├─ Decrypt MMKV file (AES-GCM: 4B size + 16B IV + ciphertext + 16B tag)
    │      ├─ Parse decrypted plaintext for DB path → 64-char hex key mappings
    │      ├─ Verify each candidate via verify_enc_key()
    │      └─ Return key_map (partial or complete)
    │
    ├─ [EXISTING] Memory scan for remaining salts
    │      ├─ x'hex' regex scan (old 4.1.9 format)
    │      ├─ cross_verify_keys()
    │      └─ _targeted_salt_scan()
    │
    └─ save_results()  ── [EXISTING]
```

## 3. Components

### 3.1 `_extract_keys_from_mmkv(db_dir, db_files, salt_to_dbs, print_fn)` — NEW

**File:** `src/key_scan.py` (new function, ~80 lines)

**Purpose:** Extract DB encryption keys from MMKV config files without requiring a running WeChat process.

**Input:** db_dir path, db_files list from collect_db_files(), salt_to_dbs mapping, print_fn callback.

**Output:** `key_map` dict `{salt_hex: enc_key_hex}` for all found keys.

**Steps:**

1. **Find MMKV directory:** Locate `db_storage/MMKV/` under `db_dir`.
   - If directory doesn't exist → return empty dict (old version, skip).

2. **Extract wxid:** Parse wxid from db_dir path (e.g., `...\wxid_cpyn7pe119rs21_10e8\db_storage` → `wxid_cpyn7pe119rs21_10e8`).
   - Clean via `_clean_wxid()` (strip suffix after 2nd underscore) → `wxid_cpyn7pe119rs21`.

3. **Enumerate MMKV files:** List all `.mmkv` files (skip `.crc` files).
   - Extract hex codes from `f<hex>tinfo.mmkv` pattern filenames.
   - Also include non-pattern files like `storage_common` with a default code (or wxid-only).

4. **Derive AES key per code:** For each unique code:
   ```python
   aes_key = hashlib.md5(f"{code}{wxid_clean}".encode()).hexdigest()[:16].encode('ascii')
   ```
   This is a 16-byte ASCII key (AES-128).

5. **Decrypt MMKV file:** Read file, parse header (4B total_size LE + 16B IV), decrypt with AES-GCM.
   - Skip files locked by WeChat (IOError → continue).
   - On GCM auth failure → wrong key, skip this code.
   - Requires `pycryptodome.Crypto.Cipher.AES`. If not available, return empty dict.

6. **Parse plaintext:** Search decrypted data for DB relative paths (both `\` and `/` separators).
   - For each path match, scan nearby bytes (next 256B) for 64-char hex strings.
   - Each 64-char hex is a candidate `enc_key`.

7. **Verify candidates:** Test each candidate against the corresponding DB's page 1 using `verify_enc_key()`.
   - On match → add to `key_map`.
   - Stop scanning a code once all salts for its associated DBs are found.

8. **Return** `key_map`.

## 4. MMKV File Format

```
Offset  Size    Description
0       4       Total encrypted size (uint32 LE) = file_len - 4
4       16      AES-GCM initialization vector (random per file)
20      N-16    AES-GCM ciphertext (N = total_size from offset 0)
20+N-16 16      AES-GCM authentication tag
```

Decrypted plaintext contains MMKV key-value pairs with length-prefixed encoding:
```
[uleb128_key_len][key_bytes][uleb128_value_len][value_bytes]
```

We search for DB path strings (e.g., `message\message_0.db`) and extract 64-char hex values nearby.

## 5. Error Handling

| Condition | Behavior |
|---|---|
| `db_storage/MMKV/` doesn't exist | Return empty dict, fall through to memory scan |
| MMKV file locked by WeChat | Skip file, try others |
| AES-GCM auth failure | Wrong key for this code, skip |
| pycryptodome not installed | Log warning, return empty dict, fall through |
| No hex keys in decrypted plaintext | Wrong code or empty MMKV, skip |
| Partial keys found | Return what we have; memory scan handles rest |

## 6. Backward Compatibility

| Scenario | MMKV Works? | Memory Scan Works? | Result |
|---|---|---|---|
| WeChat 4.1.9 (no MMKV dir) | N/A (skip) | Yes | Memory scan succeeds |
| WeChat 4.1.10.x (MMKV files exist) | Yes | No (no keys in memory) | MMKV succeeds |
| WeChat 4.1.10.x + WeChat not running | Yes | No (no process) | MMKV works offline |
| Wrong wxid/codes (edge case) | No | Yes (if 4.1.9) | Falls through to memory scan |
| Future version (unknown) | Try first | Try next | Whichever works |

The existing memory scan code is **unchanged** — MMKV is purely additive as a new first strategy.

## 7. Testing

**Validation test:** Run MMKV extraction against current WeChat 4.1.10.27 installation with known-good keys.
- Compare extracted keys against `.wechat_exp_config.json` (28 known keys).
- All 28 should match exactly.

**Fallback test:** Temporarily rename `db_storage/MMKV/` directory, verify memory scan still works for old versions (or gracefully reports no keys for new versions).

**Edge cases:**
- Empty MMKV directory → graceful skip
- Corrupted MMKV file → skip that file, continue
- WeChat holding file lock → skip locked file, try others
